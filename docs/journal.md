## 2026-08-29 · ⚖️ 决定 12 正式定论：P1（局部二次 OCR 修复 glue）降级

**状态**：DEPRIORITIZED / 降级。

**依据**：用当前真实 PP-OCRv6 引擎重新生成了 15 份 fixture（不是当初
定 P1 优先级时依据的那份过时 `demo_ocr_pp.json`），共 1,111 行 OCR，
10 份有 `ground_truth.json` 可比对。

- 此前用于支持 P1 立项的 4 个历史 glue 案例（`JENNIFERWASHINGTON`/
  `JOHNBDOE`/`iJANEDOE`/`JANEDOE:`），在当前引擎下**均不再复现（0/4）**。
- 当前 `suspiciousGlue` 检测器在这 1,111 行里标出 16 行（1.44%），
  逐条人工核对**全部是误报**（信用卡品牌名、表格栏目名、水印/logo
  乱码），**precision = 0%**。
- 因此当前**没有观察到真实 glue 可供二次 OCR 修复**，也无法证明二次
  OCR 存在正向收益。
- 此前对典型 false-positive 内容（`AMERICAN`/`WInILLDDOUTU,LVIU` 等）
  做过的真实二次 OCR 实测（P1-C，见前面几条记录）还显示存在**误伤和
  confidence 降低**现象——不是"没有收益"，是"净值可能为负"。

**为什么 15 份就够下结论，不用等 `IRS_cp503` 补测完**：16 个 suspicious
全部是假阳性，这已经不是"样本太少所以不确定"，而是 detector 本身表现
出明确的问题——它现在找不到真正的 glue，反而把正常文本、栏目标题、
水印、logo 当成可疑。`IRS_cp503` 能扩大 benchmark 覆盖度，但不该阻塞
这个工程决策——即使它最后测出还有 1 个 glue 案例（4 个历史案例里
3 个消失、1 个还在），也不足以推翻结论：真正要证明的是「glue 出现
频率 × 二次 OCR 修复成功率」能不能抵消「detector 假阳性 + 二次 OCR
误伤 + 额外算力成本」，现在的数据显然还没到那个量级。

**结论**：现有证据不支持继续投入 P1。保留现有二次 OCR 代码
（`suspiciousGlue.js`/`secondPassOcr.js`/`p1-experiment.html`/
`fixture-regen.html`）作为实验性能力，不删除，但不再继续优化
suspicious/glue detection，不把它列为当前主 pipeline 的优先开发方向。

**什么情况下该推翻**：未来如果新的 benchmark 发现具有统计意义的真实
OCR 粘连错误，并且能证明二次 OCR 能稳定提高字段级准确率、误伤成本
可以接受，再重新评估 P1——不是现在就永久关闭这条路。

**下一步**：注意力转向这次 benchmark 真正抓到的、有统计意义的问题——
`DMV_Registration` 的金额漏检（`$95` 被 OCR 读成 `S95`，`$` 认成了
`S`），这直接拖累了这次 amount recall（9/10）——这是**真实发生**的
失败，不是假设性的，而且可能牵涉到决定 06（"金额只认带 $ 的写法"）
在这种误读场景下该怎么办，比继续把 `suspiciousGlue` 从 0% precision
调出一个好看的数字更值得投入。见下一条记录。

## 2026-08-29 · ✅ 新增 fixture-regen 工具：用当前真实引擎重建基线

**背景**：上一条记录说的问题——`demo_ocr_pp.json` 可能跟不上当前引擎
版本——不能靠猜，得靠重新跑一遍全部样本、拿真实数据说话。加一个独立
浏览器工具，专门做这件事，不改任何现有算法代码。

**新增两个文件**：

```
frontend/fixture-regen.html              独立页面
frontend/src/fixtureRegen/main.js        页面逻辑
frontend/src/fixtureRegen/readingOrder.js  从 App.jsx 原样搬来的行排序逻辑
```

**这个工具做什么**：用户在自己电脑上批量选中 `demo_image/` 里的图片
（PDF 格式的两份 IRS 通知除外，需要先自己转成图片），对每一份都：

1. 用跟主应用一致的 `enhanceDocumentImage` 预处理 + `ocr.predict()` 参数
   跑一遍真实 OCR；
2. 用**原样从 `App.jsx` 搬过来**（不是重写、不是简化版）的
   `buildSpatialReadingOrder`（以及它依赖的 `detectLikelyColumns`/
   `sortColumnLines`/`buildVisualRows`/`isSameTextRow`/
   `getVerticalOverlapRatio`）算出跟真实用户看到的一致的行顺序——
   之前 P1-C 页面为了简单跳过了这一步，这次为了 fixture 的保真度补上，
   因为很多脱敏/抽取逻辑（比如收件人地址块往上下扩 3 行）是依赖行顺序的；
3. 直接复用（不重新实现）`fieldExtractor.js` 的 `extractLetterFields`，
   跟 `ground_truth.json` 比金额和到期日 recall；
4. 直接复用 `suspiciousGlue.js` 算 suspicious rate；
5. 检查决定 12 里那 3 个已知粘连字符串这次还在不在。

结果实时显示在页面表格里（新旧行数对比、confidence、金额/日期对错、
suspicious 统计、粘连字符串状态），也能导出一份完整 JSON。

**为什么要把 `buildSpatialReadingOrder` 这一坨从 `App.jsx` 里搬出来**：
它是纯函数，不依赖 React/JSX，逐字复制过来风险很低；但如果以后
`App.jsx` 里这几个函数改了逻辑，这个工具文件不会跟着变——这是刻意
接受的技术债，因为这终究是个一次性/低频跑的基线工具，不是要长期维护
两份互相同步的核心链路代码。

**没做的事**：没有自动把结果写回 `demo_ocr_pp.json`——工具只生成、
下载，实际替换/拆分（`wm_trash_bill` 那条要单独放进
`demo_ocr_photo.json`）留给拿到结果之后手动做，避免在没看过数据之前
就自动覆盖仓库里的基线文件。也没有处理 `IRS_cp503`/`IRS_cp501`
（只有 PDF）——这两份需要用户先自己转成图片。

**验证**：`npm run build`（主应用）不受影响；`fixture-regen.html` 用
Playwright 确认能加载、所有 import（`fieldExtractor.js`/
`suspiciousGlue.js`/`ground_truth.json`/`demo_ocr_pp.json` 等）都解析
成功、无 JS 报错——真实批量重跑本身要在用户电脑上跑才能验证。六层
回归全绿（这次改动完全没碰 `utils/` 里任何被测试覆盖的文件）。

## 2026-08-29 · ✅ P1-A/P1-B：可疑粘连检测器 + 二次 OCR 编排逻辑（独立实验模块）

**背景**：决定 12 的 P1 排的是"对可疑粘连结果做局部二次 OCR"。这次先做
一个很小、可验证的实验，不碰主链路，也不改 PaddleOCR 参数——新增三个
独立文件（`suspiciousGlue.js`/`secondPassOcr.js`/
`secondPassOcr.experiment.test.mjs`），`App.jsx`/`imagePrep.js`/
`contentRedactor.js`/`fieldExtractor.js` 一行没动。

**这次能在沙箱里跑出真实数据的部分（P1-A）**：`suspiciousGlue.js` 是纯
逻辑判定——不判断"是不是姓名"（那是 `contentRedactor.js` 的事），只判断
"这一行长得像被粘连了、值不值得花一次算力重跑"。在全部 18 封 demo 信
（1226 行）上跑了一遍：

```
total lines: 1226
suspicious lines: 64
suspicious rate: 5.2%
known glue case recall: 5/5（JENNIFERWASHINGTON / JOHNBDOE /
                              iJANEDOE / JANEDOE: / JAMES&KARENQ.HINDS）
```

`suspicious rate` 是成本指标，不是准确率指标——衡量的是"这套规则会让
多少行排队去做二次 OCR"，5.2% 现在看不算离谱，具体划不划算留给以后
真跑起来后再判断。bbox 宽度相对字符数偏宽这条按用户要求压成了弱信号
（+10 分，阈值 50 分），不会单独决定 suspicious。

**这次只能验证代码逻辑、不能验证真实能力的部分（P1-B）**：
`secondPassOcr.js` 分两层——像素层（裁切/放大/灰度/对比度，需要浏览器
Canvas API，沙箱里跑不了）和编排层（引擎、裁切函数都是注入依赖，可以
用 mock 在 Node 里测）。`compareCandidates` 按用户要求不选 winner，只
产出结构化对比记录（`original_text`/`candidate_text`/两边 confidence/
`changed`/`change_type`/`reasons`），原始识别结果永远不会被覆盖。用 4
个手工构造的场景（成功拆开 / 完全没用 / retry 加了空格但 confidence
反而更低 / retry 把字符读错）验证了这套编排代码本身没有 bug——**这不
代表真实 PaddleOCR 的二次识别能力，只代表这套代码逻辑是对的**。

**测试自己的过程中抓到两个真 bug**（写代码时就发现了，不是等本地跑
才发现）：

1. `runSecondPassOnLine` 里，`engine.predict()` 返回的 `score` 是
   PaddleOCR-js 原始的 0–1 区间，直接拿去跟 `line.confidence`（已经
   乘过 100 的 0–100 区间，比如 fixture 里的 `99.94`）比较，会把
   "本来差不多"误判成"candidate confidence 掉了 99 个点"——所有 retry
   都会被污染成"看起来更差"。修法是换算成同一个区间，再补一条回归
   断言防止再退化。
2. 测试脚本里手工构造 mock 场景时，直接调 `detectSuspiciousGlue(line)`
   没传 `context`（`pageHeight`/`charWidthBaseline`），导致"位于页面
   上方"这条弱信号缺失，`trigger.suspicious` 对着已知案例算出了
   `false`——不是检测器本身的 bug，是测试场景没有还原真实调用方式
   （P1-A 是按整份文档跑 `scanDocumentForSuspiciousGlue` 的）。补上
   `context` 并加了断言防止这个不一致再发生。

**产出**：`frontend/src/utils/p1-results/` 下三个 JSON——
`suspicious-lines.json`（P1-A，真实检测结果）、
`candidate-comparisons.mock.json`（P1-B，MOCK 标签清清楚楚）、
`experiment-summary.json`（汇总 + P1-C 的占位说明）。每个文件顶层都有
`mode` 字段，防止以后 MOCK 结果和真实结果被混着分析。

**没做的事（P1-C，必须本地做）**：这个沙箱环境的出站网络策略挡住了
PaddleOCR-js（以及试过的替代品 tesseract.js）需要的模型文件域名，没法
在这里初始化任何 OCR 引擎。**"二次 OCR 到底能不能把
`JENNIFERWASHINGTON` 拆回 `JENNIFER WASHINGTON`"这个问题，本次任务没有
回答，也回答不了**——需要在能连外网的本地浏览器里，用 `secondPassOcr.js`
文件末尾写好的接入方式，接真实 `getOCREngine()` 和真实 canvas，对着
这 5 个已知案例实际跑一遍，并且要跟 ground truth 比较，不是"retry 看起来
更合理"就算数。18 封信、5 个已知案例，只够支撑 feasibility test，不足以
证明"二次 OCR 提升了多少准确率"——那需要对每个目标字段建立 ground truth，
还没做。

**决定**：下一阶段的开发优先级是——

```
本地 OCR → 本地 PII 检测 + bbox → 图片上真正遮盖 → 脱敏图片 → LLM Vision 理解全文
```

具体排序：

1. **PII Ground Truth + bbox 遮盖 recall 测试**（最高优先级）——不是继续测

3. 姓名 NER（一个约 14.7MB 的小型 ONNX 模型，只负责 PERSON/ORG/LOCATION）
   ——但只在有了 1 的 recall 基线之后再加，不然"加了 NER 之后到底好了多少"
   没法量化，只能凭感觉。
4. 金额/日期本地交叉验证——如果这条链路证明必须靠业务规则兜底才安全，
   再回来加。

**这条决定不推翻决定 01，也不是要删掉 `FieldExtractor`**——说清楚边界：

- `FieldExtractor` 继续保留在代码里，不删除、不冻结成只读。
- **金额和到期日的最终结构化结论，永远来自本地 `FieldExtractor`，不来自
  LLM**——这条跟决定 01 完全一致。LLM Vision 以后负责的是"整封信在说什么、
  下一步该做什么"这类语义理解，即使 LLM 顺手读出了金额，也不能覆盖本地
  金额（现在的实验面板已经是这么做的：AI 读到的数字只在单独一块"仅供参考"

- 如果本地 PII 检测的召回率长期上不去（比如 NER 加上之后还是有一类隐蔽
  PII 稳定漏检），需要重新评估这整条"打码图片发给 LLM"的架构是否可行，
  到时候再回来重新讨论，不是现在就下结论说这条路线一定能走通。
- 如果以后发现某一类账单（比如某种法律文书）必须靠本地业务规则才能保证

**什么情况下该推翻**：LLM Vision 在打码图片上的理解准确率长期达不到能让人
放心的水平（需要用第 1 条的 recall 测试 + 真实理解准确率数据来判断，不是
凭感觉），或者本地 PII 检测的召回率无论怎么加规则/加 NER 都上不去。

## 2026-08-29 · 🐛 `SMITH,BRENDA` 逗号紧贴两个词，姓名检测直接漏过去

**被「在图片上打码再发给 AI」这个实验炸出来的**：为了测试"本地画黑框挡住个人信息、
再把图片发给视觉模型"这条路线准不准，先把 `buildTranslatablePayload` 判定为

没有任何空格——这是 OCR 常见的输出形态，之前只在 `BAKER, NATE`（带空格）这种
样本上测过，没测过逗号紧贴的情况。

**修法**：`\s+` 改成 `\s*`（允许零空格），其余判定逻辑不变（`STATE_CODES` 排除

**验证**：`contentRedactor.recall.test.mjs` 召回从 21/32 提升到 23/32，六层回归

的文字列表时，「少了一行」很难一眼看出来，但画成黑框之后"这里应该被挡住却露出来了"

## 2026-08-28 · 🐛 Medical_Invoice 金额明明抽对了，却还是显示「没能确认」

**被用户在实测三态拆分后追问炸出来的**：上一条改动把"要不要交"（`isPaymentDemand`）
和"看起来和缴费有关"（`amountLooksPaymentRelated`）拆开之后，用户又问
「为什么还是没有显示金额」——查下去发现这不是一个 bug，是两个。

**根因一：`detectAmountColumn` 一直在用带 `$` 门槛的 `parsePureMoney`，把自己的分项全过滤掉了。**

Zylker 发票样本整页只有 Total 一处带 `$`（`$14,595.00`），Sub Total
`13,900.00`、Tax `695`、三个分项 `900.00`/`10,000.00`/`3,000.00` 全是裸数字——
这本来是决定 06 故意要的效果（防止把任意数字当金额）。但 `detectAmountColumn`
是**佐证**逻辑，不是候选生成，它需要看到整列（哪怕列里有裸数字）才能判断
"这一列凑得上账"。用严格版 `parsePureMoney` 导致 `moneyLines.length` 永远
只有 1，连不上列，`amount_in_column` 这条佐证从头到尾没机会跑。

**修法**：新增 `parsePureMoneyLoose`（`$` 可选的宽松版），**只给
`detectAmountColumn` 内部用**，候选生成（`parseCandidateValue`/主循环）继续
用严格版 `parsePureMoney`——决定 06 的门槛管的是"什么能当候选"，不是"佐证时
允许看到什么"，两者不冲突。

**根因二：`findSumRelation` 的"分项数量多者优先"选错了链条。**

`detectAmountColumn` 修好之后列里是按页面从上到下排的
`[900, 10000, 3000, 13900, 695, 14595]`。两条链都能对上账：
`900+10000+3000=13900`（count 3，验证的是 Sub Total）和
`13900+695=14595`（count 2，验证的才是真正的 Total）。旧写法"谁的分项多
选谁"选中了前者，于是"分项之和验证"验证的是小计不是总额——账本身算对了，
却因为链选错了而报"对不上"。改成优先比较 `end`（更靠后 = 更接近页面最终
合计），`count` 只在 `end` 相同时做 tie-break。

**根因三（这才是用户问题的直接原因）：`howMuch` 的 if/else 链把
"这是不是要交的那笔"（`isPaymentDemand`）和"这个数字本身有没有抽对"
（`amount.trusted`）当成了一件事。**

三态拆分只改了内部字段和判断依据，没有改消息模板——`isPaymentDemand` 为
false 时无论 `trusted` 是不是 true，都落到同一句"没能确认具体金额"。
Medical_Invoice 的 Total 锚点只有 35 分，赢不了 `isPaymentDemand` 要求的
72 分门槛，但金额本身早就靠列校验立住了（`trusted: true`）——用户看到的
应该是"这个数，只是不确定是不是要交"，不是"这个数没读出来"。

**修法**：在 `amountLooksPaymentRelated` 分支前插入一支
`amountLooksPaymentRelated && fields.amount.trusted`，把确认的数字念出来，
只在"是不是要交"这一层打问号。

**验证**：`accuracy.test.mjs` 金额列从改动前的"看不准"变成 15/15 100%
（`payment_action` 维度仍是 14/15——Medical_Invoice 这一项没变好，这是
预期内的：`AMOUNT_ANCHORS` 目前只编码"这个词在账单里有多常见"（权重），
不编码"这次出现是不是一条付款指令"，"Total" 这种词天生两种场合都用，
35 分锚点本来就不该越过 `isPaymentDemand` 的门槛——这个缺口在决定 09 附近
已经写明是要等真实冲突样本才能安全解决的，这次不动它。六层回归全绿，
`Medical_Invoice` 现在人读到的是：

> 信上写的金额是 14,595.00 美元，但小助手不确定这就是您需要交的那一笔。

而不是此前的"没能确认具体金额"。

## 2026-08-28 · ✅ 姓名检测合并成一份，`detectLocalPII` 现在也认识 [NAME]

**被用户实测 Allina Health 医院账单炸出来的**——「查看最终 OCR 文字」
调试面板里，地址、电话都变成了 `[ADDRESS]`/`[PHONE]`，但「JANE DOE」
原样显示，用户以为脱敏漏了。

**根因不是漏检，是这个项目里一直有两套互不相干的姓名判定**：

1. `App.jsx` 的 `detectLocalPII`——16 类正则检测器，**压根不认识姓名**
   （`contentRedactor.js` 开头注释早就写着这句），驱动的是「查看最终
   OCR 文字」这个调试面板（`redactedOcrText`）。
2. `contentRedactor.js` 的 `buildTranslatablePayload`——多了姓名/
   收件人区块检测（`looksLikeName`），但它的输出**现在没有接到任何
   UI 上**，只是算出来、没地方显示（`App.jsx` STEP 3.6 的注释原话）。

用户测试时看到的是第 1 套（弱的那套），第 2 套（强的那套）一直存在
但没人看得到——不是"脱敏漏了姓名"，是"漏了的那一套刚好是唯一
显示出来的那一套"。

**改法**：`looksLikeName` 从 `contentRedactor.js` 导出，`App.jsx`
新增 `collectNameDetections(text, lines)`，按 `lines` 顺序累加字符
偏移换算每一行在 `text`（`lines.map(l=>l.text).join('\n')` 拼出来的）
里的起止位置——不用字符串搜索，因为「JANE DOE」这类内容在页面上
可能重复出现，搜索会分不清是哪一次，按行顺序累加不会有这个问题。
`detectLocalPII` 现在接收 `lines`，姓名整行替换成 `[NAME]`，和
`[ADDRESS]`/`[PHONE]` 走同一套 pipeline、同一套判定逻辑
（`looksLikeName` 只有一份实现，两处都调它，不是两份各自维护的代码）。

**验证时发现一个新缺口，这次没有一起处理**：`looksLikeName` 的形状
判定（第 4 条信号）要求「位于页面上方 45%」，这是为了不把
「Generation Charges」这类账单术语误判成人名而卡死的门槛。Allina
账单里第二处「JANE DOE」在「PATIENT NAME」那一行的表格里，位置在
页面偏下方，这条限制会让它漏检——用同样的方法模拟验证过：第一处

## 2026-08-28 · 🐛 金额看不准的时候，说成了「这封信里没有提到要交钱」

**被用户在真实浏览器里测 `Medical_Invoice` 炸出来的**——上一条刚把

    phrases.some((p) => p.intent === 'PAY' || ...));  // 发票模板没有"请支付"这类措辞

## 2026-08-28 · ⚖️ 决定 09：金额候选生成不再要求「先命中锚点」

**背景**：金额抽取从一开始就是「扫锚点行 → 找它附近的钱」——锚点是
候选能不能诞生的**硬性前提**。今天连续两次撞到同一个根因：

- IRS CP504「Amount dueimmediately」被 OCR 粘连，没有锚点匹配到，
  候选**一个都没生成**——分项求和明明对得上（$9,444.07+34.98+54.48
  =9,533.53），但决定 08 那套"分项求和参与排序"根本没机会派上用场，
  因为排序的前提是"先有候选"，这次连前提都不满足。
- OC 地税单「$1,822.02」那次，真正的付款指令行的锚点因为图片上的
  批注框被 OCR 完全漏读，候选池里只剩一个碰巧沾了裸 `TOTAL:`
  （权重 35，其实是税率分摊表的解释行）的候选，误打误撞赢了。

两次根因是同一件事：**候选生成阶段就把证据不全的候选提前淘汰了，
后面写多少排序逻辑都补不回来**。用户直接指出了这一点——问题不是
"证据不够多类",是"生成候选的方式本身就是错的"。

**改法**：`findAmountAnchorNear` 是 `findValueNearAnchor` 的镜像版
本——原来是「从锚点出发找值」，现在反过来「从每一个带 $ 的值出发找
锚点」。具体地：

1. 页面上每一行只要 `parsePureMoney`/`findMoneyInText` 能读出金额
   （决定 06 的门槛不变，必须带 $），就先成为候选，不管附近有没有
   锚点。
2. 对每个候选，用跟原来完全相同的空间关系（同行/左边/正上方，含
   两行表头合并 `anchorTextWithHeaderAbove`，直接复用没有重写）去
   找附近最强的锚点——找不到就是「没有语义证据」，不是「不算候选」。
3. 打分公式跟决定 08 一样没变：`语义权重 + 空间分*0.3 + 分项求和
   命中加 15 分`。区别只在于：现在**没有锚点的候选也会被打分**，
   如果它的空间关系够强、分项求和对得上，还有机会在排序里追上来，
   而不是从生成那一步就被排除在竞争之外。

**这次刻意没做的**：候选间的 margin 判断/abstention（"第一名和
第二名分数接近就不确定"）——那是排序层要做的事，这次只改生成层，
按最小改动的原则一次只动一处。也没有扩大到 3 类以上的证据（Frequency
/Visual 等），跟这次会话最开始定的范围一致。

**验证**：13 封信的 `ground_truth.json` 全量跑过，改前改后**结果
完全一致**（类别 12/13、金额 13/13、付款方式 13/13、到期日 13/13、
发信日期 12/13，一个数字都没变）——这次改动没有让任何一个已知答案
变化，纯粹是把候选生成的方式换了一种更不容易漏的写法。六层回归
全绿。验证过程中还带出一个真回归：候选生成如果直接用 `moneyParser`
的 self 分支（`findMoneyInText`），会漏掉 `parsePureMoney` 才认得的
`(123.45)`/`123.45 CR` 贷记写法——AT&T 账单的 `-$6.33` 一度被读成
了 `+$6.33`，加了 `parseCandidateValue` 优先走 `parsePureMoney`
才修好。

**什么情况下该推翻**：如果发现候选池变大之后（现在每一个带 $ 的
值都会生成候选，不止锚点附近的），某封信里出现"没有锚点但恰好
分项求和对得上"的噪声候选把真正答案挤掉——那说明单纯的加权求和
撑不住更大的候选池，需要做真正的 tier/margin 判断，而不是继续加
权重。到那一步再重新开一条决定，不要回头改这条。

## 2026-08-28 · 🐛 「January 28,2019」这种逗号不带空格的日期，整条解析不出来

**被 `demo_image/IRS_cp501.pdf`（官方 CP501 样本）和 `IRS_cp503.pdf`
（官方 CP503 样本）炸出来的**——这两封信的到期日、发信日期全都抽不出来，
而且这次不是锚点词的问题，是**日期本身解析失败**。

**根因**：`findDatesInText` 里「February 5, 2024」这种写法的正则是
`([A-Za-z]{3,9})\.?\s+(\d{1,2})(?:st|nd|rd|th)?,?\s+(\d{4})`——日和年
之间要求 `\s+`（至少一个空格）。IRS 官方样本上「January 28,2019」
逗号后面直接贴着年份，一个空格都没有，`\s+` 匹配不到零个字符，
整条日期解析失败——不是锚点没命中，是锚点命中了、旁边那格里的
文字根本没被认成"日期"，`findValueNearAnchor` 找不到值。

这比锚点词的 `\b` 断裂更隐蔽：锚点断了只丢一处，日期解析器断了，
**这份文档里所有用这个格式写的日期，到期日和发信日期一起丢**——
CP501 和 CP503 两封信原本都是"金额对、日期全军覆没"。

**改法**：日和年之间的 `\s+` 改成 `\s*`（允许零个空格）。前面
「月份 + 空格 + 日」那一段没改，OCR 目前观察到的粘连都发生在
逗号之后，不在月份和日之间。

**顺带在同一份 CP501/CP503 上加了两条新的日期锚点**（跟这个
日期解析 bug 是两回事，但同一轮验证一起发现的）：
- `\breceived\s*by` —— CP501「Amount due, to be **received by**
  February 19, 2019」换行后单独一行被粘成 `receivedbyFebruary...`，
  原来 29 条锚点没一条认这个说法。
- `\bamount\s*due\s*by` —— CP503「**Amount due by** January 29, 2018」
  被粘成 `AmountduebyJanuary...`，`\bdue\s*by\b` 要求 due 前面是词
  边界，但紧贴着 Amount 的 t，没有边界，锚点不触发。跟 IRS CP504
  那次「amount due immediately」是同一类问题，同样加一条整体覆盖。

**改完之后**：CP501——金额 $9,533.53、到期日 2019-02-19、发信日期
2019-01-28，三项全对；CP503——金额 $9,533.53、到期日 2018-01-29、
发信日期 2018-01-08，三项全对。

更不做机器学习排序。

1. 新样本进来后，某个真实候选因为这 15 分被错误地压过了原本该赢

3. 样本量到了几十封以后，`ARITHMETIC_MATCH_BONUS` 这类拍脑袋的

   learning-to-rank，而不是继续手调这一个数字。

- 姓名 40% → **只能靠 NER**，加多少条正则都补不上「没有形状」这件事
- 地理信息 78% → `WINDBELL` / `MESQUITE` 是地址组件，**可能改条规则就够**，
  比 14.7MB 的模型便宜得多。先试规则，试不通再上模型。

**门槛设成「不许比现状更差」，不是「必须 100%」**

定成 100% 的话这个测试今天就是红的，而**红着的测试等于没有测试** ——
大家会习惯性忽略它。定成现状（16/21），任何**新增**的泄露立刻被抓到，
已知那五个漏在输出里单独列着，不会被忘掉。修好一个就把门槛往上调一格。

**下一步顺序定了**：先试规则补地址（便宜），再上 NER 补姓名（贵但无可替代），
每一步都用这把尺子量。

## 2026-08-27 · ✅ 版面还原 —— 别把二维的信压成一维的字

**用户发现的**：OCR 认字很准，但**行的顺序和排版不对**。他给了两个例子：

```
online tools for billing and more. Have a
07/02/2025: $ 92.05                          ← 右栏的金额插进了左栏句子中间
question? Check our support center or start

Previous Balance / Payments / Adjustments / Current Invoice / Total Account
+ / + / + / Charges / Balance Due
0.00 / 0.00 / 0.00 / 87.05 / 87.05           ← 哪个数字属于哪一栏，全丢了
```

**我之前判断错了一件事。** 早前说过「阅读顺序不影响字段抽取」——
那是对的（抽取用 bbox 几何，不看数组顺序）。
**但一旦要把文字发给 LLM，顺序就突然变成头等大事。**

**不修排序，改成不压扁**

根本问题不是「排错了」，是**把二维压成了一维**。压扁的那一刻信息就没了，
再怎么排都补不回来。所以按坐标把行摆回二维，拼成一张「文字画」。

摆回去之后，两行叠着的表头、数值属于哪一栏，**全都自己浮出来了**。

**三版才调对，中间那版的教训值得记**

```
v1  按固定行高量化      能用，但表格数值行被切成两行
v2  按垂直重叠聚类      表格完美，但正文被**链式吞并**成一行
v3  重叠聚类 + 行带不扩张  ✅
```

v2 错在让行带跟着成员一起长：一行吃掉下一行、再吃下下一行，整段正文挤成一条。
v3 以最靠上那条为准，只有跟**它**重叠够多的才算同一行。

**刻意不做的事**

这个函数**不排序、不猜阅读顺序、不合并栏目**，只按坐标摆回去。
「谁该读在谁前面」留给看到版面的那一方判断 ——
我们自己猜反而会猜错，早期那套 `buildSpatialReadingOrder` 就是教训。

代价 +45% 字符，基本都是空格。8 条断言钉住。

## 2026-08-27 · 🐛 期限字段：先混为一谈，再过度设计，最后才砍对

**一天之内在同一个字段上错了两次，方向相反。值得完整记下来。**

**错误一：把法律和猜测混成一个字段**（用户问出来的）

> 「不同公司按订阅时间付款，加罚时间也不同，不能这样规定。」

原来一个 `deadlineNorm` 里同时装着：

```

电费「通常出账后 20 天到期」                        ← 我编的概括
```

两句语气一样自信，第二种就成了「自信的错误答案」——
**这个项目防了一路的东西，我在知识库里又造了一遍。**

**错误二：修的时候过度设计**（用户又问出来的）

> 「有必要这么复杂吗」

我的修法是拆成 `statutory` / `varies` 两档，给 32 条 `varies` 各写一句
一模一样的「以信上印的为准」，再配一条断言去检查它们不含天数。

**同一句话存 32 遍不是设计，是官僚主义。** 而且那句话本来就该由界面
在读不到期限时自己说，根本不该存进数据里。

**最后砍对的版本**

`deadlineRule` 改成**可选字段**：有法定规则就填（必须写明依据），没有就不写。

**一、一个字段如果同时装得下「法律」和「我的概括」，迟早会把后者说成前者。**
该分开的时候不要图省事合并。

**二、被指出问题之后，第一反应往往是「加一层结构去管住它」——
而正确答案常常是「把不该存的东西删掉」。**
加结构感觉像在负责任，其实只是把复杂度换了个地方放。

先问「这个东西该不该存在」，再问「怎么管住它」。

## 2026-08-27 · ✅ 两行表头合并 —— WM 的 87.05 走正门拿到了

**用户的问题**：「为什么不能直接返回 Total Account Balance Due 下面那个 87.05？」

**答案是：我们早就拿到了，是自己不敢用。**

```
Total Account      ← 表头第 1 行
Balance Due        ← 表头第 2 行   ← 锚点只看得到这半句
    87.05          ← 正下方，抽出来了
```

裸的 `balance due` 权重 88，而「不需要佐证就直接采信」的门槛是 92。**差 4 分。**

**先试了最省事的办法，然后否掉了**

把 `balance due` 从 88 提到 92，跑全量 —— 八个套件一个没炸。
但还是否掉了，因为想到一个真实反例：分期付款账单上会同时印着

```
Remaining Balance Due   $1,200      ← 欠款总额
Amount Due This Month   $100        ← 这次要交的
```

裸的 `balance due` 指哪个要看上下文。**测试全绿不等于安全 —— 只说明我们的
11 封语料里没有这种信。** 全局提权重就是在赌下一封信不是分期账单。

**改成把信息读全**

1. 新增锚点 `total (account) balance due` = 95。带 `total` 的那句没有歧义，
   裸的 `balance due` 留在 88 不动
2. 匹配锚点时，**把正上方那一行接上来再试一次**，取更强的那个

人一眼就把「Total Account」和「Balance Due」读成一句，我们也该。

**中途炸了一个，限制条件是被炸出来的**

第一版合并规则太松，OC 房产税单当场挂掉：

```
Total Amount Due    $4,281.10
First Installment   $2,140.55     ← 跟上一行合并成「Total Amount Due First Installment」
                                     2,140.55 也成了「总额」→ 两个总额打架 → 都不敢用
```

**区别在于：真正的两行表头，上面那行右边是空的，值在两行的下面。**
而「Total Amount Due $4,281.10」本身就是完整的一对，不是半句话。

所以加了限制：**上一行如果自己右边就带着值，不许被当成前缀。**

**这件事最值得记的一点**

同一个结论（报出 87.05），今天走过两条完全不同的路：

```
早上：放松确认标准  —— 让证据不足的也过关     ❌ 已撤销
现在：把信息读全    —— 证据本来就够，是我们没读全   ✅
```

**判据从头到尾一次都没变**：能验证就说，不能验证就闭嘴。
变的是「能不能读全」，不是「要不要验证」。

以后遇到「这封信明明写着，为什么读不出来」，
**先问「是不是没读全」，再问「是不是标准太严」** —— 顺序反了就会开始过拟合。

## 2026-08-27 · ⚖️ 决定 06 · 金额只认带 $ 的写法

**用户的判断，我同意，而且理由比「更保险」深一层。**

今天为了让 WM 那封垃圾账单的 87.05 能被采信，我把佐证放宽过两次：

```
v1  只认带 $ 的                      WM 抽不出来
v2  整行只有一个数也算               口子太大：AT&T 的流量 3.46 会被当成钱
v3  至少一次带 $，裸数字只能追加      还留着洞：金额本身是 $3.46 时照样误判
v4  回到只认带 $ 的（现在）
```

**v3 那个折中最值得反省。** 它看起来"平衡"，实际上只是把洞变小了，
而且换来的是一条更难推理的规则 —— 要判断它对不对，得同时想清楚
「有几个带 $ 的」「有几个裸的」「它们会不会碰巧相等」三件事。

**简单的规则本身就是一种安全属性。** 一条你一眼能确认没有漏洞的规则，
胜过一条需要三步推演才能确认的规则。

**代价（如实记）**：更多信会显示「没能确认金额」。
WM 那封就退回去了 —— 顶部只有一个 `$87.05`，表格里两个是裸数字。

**为什么这个代价可以接受**：跟决定 02 是同一个取舍。
漏检只是少说几句（老人去问家人，安全），误判是自信地说错（老人照着交错钱）。

**什么情况下该推翻**
不该放松这条。真要让更多金额能被采信，正确的路是**别的方向**：
- 提高该提高的锚点权重（`balance due` 现在 88，自动采信门槛 92）
- 把两行叠着的表头认出来（`Total Account` / `Balance Due` 拆成两行是常见排版）
- 接 LLM 之后由它来判断"这个数是不是要交的钱"

**这三条都是在「怎么确认」上使劲，不是在「降低确认标准」上使劲。**

## 2026-08-27 · ⚖️ 决定 05 · 默认不问

**背景** 加「重拍提示」的时候发现一个矛盾：如果老人**故意**不拍地址和账号，
而 app 一直催他「请把整张单子拍全」—— 那这个卖点是「你的隐私归你」的产品，
就变成了一个天天催你交出隐私的东西。

**决定** **只为「要交多少」和「什么时候交」这两件事开口要求补拍。其余一概沉默。**

- 姓名、地址、账号缺了 —— 一个字都不说
- 机构名认不出 —— 显示「未知」，**但不催拍信头**

**理由**

1. **老人拍这张照片的目的就是想知道金额和日期。** 他绝不会故意把它们挡住 ——
   所以催这两样永远踩不到隐私。反过来，地址账号缺失多半是**故意**的。
2. **信头和收件人地址通常挨在一起**（信封窗口那块）。催拍信头等于可能催出地址，
   而认不出机构的代价小得多 —— 老人还是能看到要交多少、什么时候交。
3. 跟决定 02 是同一个方向：
   决定 02 是**默认不发**（没确认安全的不外发），这条是**默认不问**（没必要的不索取）。

**代价** 有些信会因为缺机构名而一直显示「未知」，准确率数字上不去。

**什么情况下该推翻**
不该。这是产品定位。将来一定会有人说「让老人补拍一下信头，机构识别率能从
60% 提到 85%」—— 那个收益不值得让 app 变成催人交隐私的东西。
要提高机构识别率，去接 LLM，别去问用户要。

## 2026-08-27 · ✅ 删掉二次 OCR，换成「告诉用户重拍」

**删了什么** `cropImageRegion` / `extractBestCropOCR` / `scoreCandidate` /
`chooseBetterOCRResult` / `runCriticalLineReOCR` / `refineCriticalOCRLines`
以及编排块和两块 UI 面板。**App.jsx 6298 → 5113 行，砍掉 1185 行。**

**为什么删 —— 三条理由**

1. **实测从没改善过任何一行**（`improved: 0`），存疑了整整一轮
2. **有确认的污染机制**：上下各扩 0.65 倍行高会吃到相邻行 →
   裁出来的所有 OCR item 被 `.join(' ')` 拼成一串 →
   分数高 5 分就替换掉原行。**为了修一个金额，可能把邻行文字塞进金额那一行**
3. **它想解决的场景，实测它解决不了** —— 见下

**第 3 条是这次新增的证据。** 用 WM 那封实拍账单直接测了二次 OCR 的核心假设
（裁出来放大能不能救回模糊的标签）：

```
全页 OCR：        「Your Payment is Due」整行没有输出
裁出来放大 4 倍：  认出来了 → "YourPayueitisvue"  置信度 82%
```

**字母上半截被照片边缘切掉了，放大只是把残缺放大。**
而且如果真把这行「补」进去，它匹配不上任何锚点，却会占一个数组位置 ——
`contentRedactor` 判断相邻是按数组下标的，等于往脱敏逻辑里插了一行噪音。

**换成了什么** `retakeHints` —— 系统本来就知道自己为什么失败
（「有一个很显眼的金额，但它没有任何锚点」），把这个原因翻译成老人能照做的一句话。

**这是唯一一个对所有信都有效的改动。** 老人重拍一次，标签完整了，问题消失。
实验证明：把那行标签补回原位，金额立刻变成「要交 87.05」。

## 2026-08-27 · 🐛 机构兜底把金额当成了机构名

**症状** WM 那封信显示「寄件机构：**$87.05**」。

**根因** 认不出机构时，兜底去挑「页面上方字号最大的一行」当机构名 ——
而这封信上字号最大的就是那个金额。

**第一版修法错了。** 我先用黑名单排除金额，结果它转头去挑了
「Visit wm.com/MyWM」；再排除网址，它还会去咬别的地方。**黑名单排不完。**

**改成白名单**：兜底挑出来的那一行必须**长得像机构名** ——
含机构词（Inc / District / Services / Waste / Management…），
或者整行大写且两个词以上（典型信头写法）。都不满足就显示「未知」。

跟决定 02 同一个取舍：白名单的代价是「更多信显示未知」，
黑名单的代价是「老人看到『寄件机构：$87.05』」。

**为什么这条值钱**：全美水电气垃圾公司几千家，机构词典永远补不完，
**兜底会一直被触发** —— 所以兜底自己必须是对的。这一条对每一封认不出机构的信都有效。

## 2026-08-26 · 🐛 文档里的「已知机构 47」错了整整一轮

**症状** `docs` 和 `README` 都写着「47 known organizations」。真实数字是 **40**。

**根因** `update-docs.mjs` 是全文数 `/kind: '/`，而 `buildLayer0` 的 highlights 里
每个 `{ kind: 'amount' }`、`{ kind: 'dueDate' }`、以及 `kind: 'zero'`、`kind: 'autopay'`、
`kind: 'unknown'` 也长这样，全被数成了机构。

**发现于** 加发信日期高亮时，机构数从 47 跳到 48 —— 加一条高亮不可能多出一家机构。
**数字自己跳出来的，不是读代码看出来的。**

**修法**
- 计数限定在 `KNOWN_ORGS` 块里数，不再全文数
- 日期锚点改成 `DATE_ANCHORS + STATEMENT_DATE_ANCHORS` 两块相加
- 顺带修了分数行正则：原来的通配符写法在加了「发信日期」这一列之后
  先匹配上了**表头**，于是文档里的「当前分数」变成了一行表头
- **README 里手写的数字全部去掉**，分数改成 AUTO 块，和 `docs` 一样由脚本生成；
  `--check` 现在也检查 README

**教训（这条最要紧）**
这个脚本存在的全部理由就是「不让文档撒谎」，**结果它自己算错了一个数，还撒了一整轮**。

自动生成不等于正确 —— 它只保证「数字和某个算法一致」，不保证那个算法数的是对的东西。
所以计数这类代码，判据要**尽量窄**：数某个具体词典块里的条目，
而不是全文搜一个碰巧长得像的模式。

写这个脚本的时候我图省事全文数，因为「反正 kind: 只在机构表里出现」—— 当时是对的，
后来加了 highlights 就不对了，而它不会报错，只会安静地多数几个。
**「现在恰好成立」的假设，就是将来的 bug。**

## 2026-08-26 · ✅ 发信日期和截止日期分开抽、分开显示

**为什么** 这两个日期混在一起，是最容易害老人做错事的一类错。Hoag 那张医院账单上

**改了什么**

- 新增 `STATEMENT_DATE_ANCHORS`（9 条）和 `STATEMENT_ANCHOR_BLOCKERS`

- 新增 3 条交叉校验：置信度 · 发信日期不能在未来（留 2 天余量）· 发信日期不能晚于截止日

- 无标签的信头日期兜底（政府信、法院信常见）。卡死四条：整行只有日期 · 在页面上三分之一 ·
  不在未来 · 没有任何带标签的发信日期。**带标签的永远优先**
- 前端两个独立的框。截止日期红框、加「要在这天之前办」；发信日期灰底细边小字、
  加「不用在这天之前办什么」—— 光写「发信日期」四个字不够，那是行话

  `accuracy.test.mjs` 加第五个维度

锚点词烂了，年份还错了两年。抽不出来，所以不显示。

### 从台账里读出来的四条规律

**1 · 同一个意思，英文有无数种写法。**
`no payment required` / `Payment is Not Required` / `AMOUNT DUE: None` / `$0.00` /
`DO NOT PAY` / `Nothing is due` —— 每次只覆盖了当时想到的那几种。**这是无底洞。**

**2 · 同一个词组，在不同上下文意思相反。**

| 原文 | 真实含义 | 曾经的误解 |
|---|---|---|
| `DO NOT PAY` | 已自动扣款 | 不是账单 ❌ |
| `Pay by Phone` | 缴费方式 | 缴费期限 ❌ |
| `AutoPay discount` | 营销话术 | 已登记自动扣款 ❌ |

**这类最难防，字面完全正确，只有上下文能区分 —— 也最适合交给 LLM。**

**3 · 自己写的正则 bug 只能靠样本暴露。**
四位数金额截断（#5）存在了整轮，六张测试图恰好都是三位数金额，运气好没撞上。

**4 · 用户发现的 bug 全在表达层。**
#21 #22 #23 都是用户读输出时发现的自相矛盾。
**这说明表达层需要的是「读一遍」，而不是更多测试** —— 现在有一致性断言在防。

## 2026-08 · ⚖️ 决定 04 · 默认零网络，联网是用户主动开启的增强

**背景** 同类产品（如 App Store 上的 AdminGuide）的架构是：默认把照片传到服务器分析，
本地处理是较新 iPhone 上的加分项。它的隐私标签申报收集 `User Content（照片）`、
`Financial Info` 并**关联到身份**。

**决定** 方向反过来：默认全部在设备上完成，联网是用户主动打开的增强功能。配套三条：

1. **不做账号** —— 没有 user ID，结构上就没有身份可以关联
2. **飞行模式可用** —— 当成功能来测试和宣传
3. **每条回答标出来源** —— 本机生成 / 需要联网，逐条可见

**理由**

1. **老人用的是旧手机。**「较新的 iPhone 可以完全本地处理」反过来读就是：旧手机照样上传。
   而这个产品的用户，恰恰是拿着儿女淘汰下来的旧手机的老人 ——
   **最需要保护的那群人走的是上传那条路。**
2. **默认设置基本没人改。** 老人不会去翻设置。默认是什么，实际就是什么。
   所以「有没有本地模式」不重要，**「默认走哪条」才重要**。
3. **可验证 > 可信任。**「我们用加密连接传输」没法验证，只能选择相信；
   「飞行模式下功能照常」五秒钟就能自己确认。对老人本人可能无所谓，
   **但决定装不装的是子女**。
4. **无账号是结构性保证。**「我们承诺不关联身份」和「我们没有身份可以关联」，
   差的不是程度，是性质。

**代价** 首次加载要下模型，比服务端方案慢；老手机性能吃紧；
没有账号意味着没有跨设备同步、没有用户行为数据。

**什么情况下该推翻** **这一条不该被推翻** —— 它是产品定位本身。
如果哪天必须默认上传，那就不再是这个产品了，应该另起一个名字。

## 2026-08 · ⚖️ 决定 03 · 知识在构建期生成，不在运行期调用

**背景** 老人需要知道「白卡年度复审要做什么」「HOA 留置权通知有多严重」。
本地模板词典覆盖不了长尾。自然的想法是运行时调 LLM。

**决定** 把 LLM 用在构建期，不用在运行期。
离线跑一次模型，把常见信件类型（估计 200–300 种）的解释全部生成出来，
人工审核后打包成 `knowledge.json`（约 1–3 MB）随 app 发布。
运行时本地分类 → 查表 → 注入本地验证过的金额日期 → 渲染。

**理由**

1. **这些知识是有限、静态、与用户无关的。** 白卡复审的规则今年和明年一样、
   张三和李四一样 —— 模型根本不需要看这封信就知道。
2. **运行期零网络。** 内容质量是 LLM 级的，但一个字节都不出设备。
   这直接支撑了决定 04 的可验证性。
3. **可审核。** 法院传票、移民补件、医保终止 —— 这类内容的建议**应该在发布前被人看过一遍**，
   而不是每次现场由模型即兴生成。对老人这个用户群体，可审核比实时更负责任。
4. **不会幻觉，可回归测试。** 同一类信永远同一个答案。这一点反复吃过亏（见表达层 bug）。
5. **零边际成本。** 没有 API 账单，所以能做真正慷慨的免费版 ——
   这是走非营利和老人中心渠道的前提。同类产品收订阅费，是因为它每次分析都有推理成本，
   **它想免费也免费不起**。

**代价** 打不中的类型只能说「这封信我不认识」；回答不了实例级问题
（「为什么这个月比上月贵 40 块」）；知识库需要随法规变化维护。

**什么情况下该推翻** 实例级问题的真实需求比预期高得多时。
但即使那时，也应该是**在预生成之外增加一条路径**，而不是替换掉它 ——
预生成那条路的离线和可审核性质是独立价值。

## 2026-08 · ⚖️ 决定 02 · 脱敏用白名单方向，不用黑名单

**背景** 要把信件内容交给外部模型，就得先脱敏。两种方向：

- **黑名单**：默认全发，检测到 PII 才挡。漏检一次 = 泄露一次。
- **白名单**：默认不发，只发明确认定安全的。漏检一次 = 少发一点内容。

**决定** 白名单方向。逐行设六道关卡，全过才允许外发。
同时**不把「发送前请用户确认」当作安全机制**。

**理由**

1. **用户看不懂英文，没人能兜底。** 黑名单的安全性押在「漏检会被人发现」上。
   而这个产品的用户**看不懂英文**，所以没人会发现。
   **兜底的人不存在，那就不能有需要兜底的设计。**
   （发送前可见的面板仍然保留，但它的定位是**知情**，不是**安全**。）
2. **把风险从「隐私事故」降级成「体验瑕疵」。**
   白名单下漏检的代价是「翻译不完整」，不是「账号被发出去」。
3. **PII 检测没有验算办法。** 金额错了有分项求和能拦。
   **人名漏了，没有任何校验和能验证它。** 这是整个系统里唯一一个
   「漏了没有任何人会发现」的模块，所以必须在方向上倒向保守。

**代价** 外发内容覆盖率 58%–91%（视信件而定），保险 EOB 只有 50%。
覆盖率太低时，模型可能拼不出完整意思。

**什么情况下该推翻** 不该推翻方向，但**闸门可以放松**，前提是先接入本地 NER 模型
把人名地址的召回率提上来。规则和模型并联、任一命中即挡之后，
才有资格讨论放宽哪几条关卡。

## 2026-08 · ⚖️ 决定 01 · 金额和日期永远由本地抽取，不交给 LLM

**背景** 接入 LLM 之后，一个自然的想法是「本地没看清的字段让模型补」。
模型确实能从图或文字里读出金额。

**决定** **LLM 永远不产出金额和日期。** 这两个字段只能来自本地抽取 + 本地校验。
即使本地失败，也宁可显示「没看准」，不让模型填。
前端渲染时，数字从 `letterFields` 取，**不从模型响应里取**。

**理由**

1. **本地有验算，模型没有。** `33.94 + 35.74 + 25.22 + 4.27 + 0.19 = 99.36`
   —— 这是算术证明。模型给一个数字，没有第二条路径能核对它。
2. **读数字是 LLM 最弱的能力，却是最高风险的位置。**
   转录数字这件事 OCR + 正则又快又可验证；模型的优势是理解，不是转录。
3. **结构上杜绝幻觉。** 数字压根不经过模型，即使模型幻觉了也不可能编错金额。
   这比在 prompt 里求它「不要编造数字」可靠得多。
4. **相关性陷阱。** 本地抽取和本地脱敏跑在同一份 OCR 上。OCR 烂到抽不出金额时，
   它同样烂到 PII 检测认不准 ——
   **「本地失败时才调 LLM」等于「恰好在脱敏最不可靠时把数据发出去」**。

**代价** 本地读不出金额时，老人得到的是「没看准」而不是一个数字。
体验上是退步，但这是有意的：**说不知道，比自信地说错好。**

**什么情况下该推翻**

- 出现了能让模型输出**可验证**的机制（比如模型同时给出它读到的分项，本地能验算）
- 或者积累了足够数据证明模型在这个任务上的错误率低于本地抽取**一个数量级以上**

## 2026-08-27

### 🐛 Bug｜信头兜底把「截止日期」说成了「发信日期」

WM 垃圾账单的手机实拍：「Your Payment is Due」这行印在纸的最上沿，
拍的时候被裁掉了，只剩下孤零零一个 `Jul 02, 2025`。

信头兜底规则（页面上三分之一 · 整行只有日期 · 无带标签发信日期）于是命中，
把它当成发信日期，对老人显示：

> 发信日期 · **不用在这天之前办什么** · 这封信写于 2025年7月2日

——正好把最后期限说反了。这是后果最重的一类错：老人会以为不用管。

**修法**：信头兜底日期如果和截止日期是同一天，就不当发信日期用
（`letterhead_date_not_due_date` 交叉校验）。带标签的发信日期不受影响。

### ✅ 变更｜从罚金措辞反推截止日期

同一张账单上，标签虽然被裁掉了，正文里却写着：

```
If payment is received after
07/02/2025: $92.05
```

「这天之后收到就加钱」＝ 这天就是最后期限。新增两条日期锚点
（`if payment is received after` 84 分 / `if paid|received|postmarked after` 82 分），
权重压在 delinquent 附近，有正牌 due date 时永远让位。

这类措辞印在正文里，不像表头那样容易被拍缺，是到期日很可靠的后备通路。

### 🐛 Bug｜「正下方」的容差是按扫描件定的，照片是斜的

上面那条锚点加完仍然抽不出来，差在 1.6 个像素：

```
「If payment is received after」  bottom = 149
「07/02/2025: $92.05」            top    = 140
```

手机拍的纸是斜的，下一行的顶比上一行的底还高了 9 像素。
原来的容差 `unit * 0.2`（≈7.4px）刚好卡在外面，整个到期日就丢了。

放宽到 `unit * 0.5`。同行右侧先判并 continue，且仍要求水平重叠 > 0.25，
不会把右边的邻居误当成下一行。

**结果**：WM 实拍从「金额对、日期缺、要求重拍」变成
金额 87.05 ✅ 截止日 2025-07-02 ✅ 发信日期 不报 ✅ 重拍提示 消失 ✅
（`fieldExtractor.photo.test.mjs` 7/7）

### 🐛 Bug｜fixture 是绿的，浏览器是红的 —— 差别是「纸拍歪了」

上面三条修完，`demo_ocr_photo.json` 全绿，但同一张照片在 5173 上
金额仍显示「没能确认」、截止日期仍显示「没找到」。

原因：那份 fixture 分辨率低、框瘦，行与行不重叠；浏览器里真实
PP-OCRv5 在 1740px 上跑出来的框更胖，斜纸让**上一行的底压到了
下一行的顶下面**：

```
「Total Account」bottom = 435   ┐ 两行表头
「Balance Due」  top    = 422   ┘ 重叠 13px
```

两行表头合并那里写的是 `if (cand.bottom > line.top) continue` —— 一票否决，
于是合不起来，只剩「Balance Due」这个弱锚点，87.05 抽得出来却不敢采信。

放宽到允许重叠半个字高（`cand.bottom > line.top + unit * 0.5`），
同时补上 `cand.top < line.top` 保证确实在上面。

**教训**：低分辨率 fixture 会给出虚假的安全感。这类容差必须用
**真实分辨率**的坐标测。新增 `fieldExtractor.slant.test.mjs`，
坐标直接抄自浏览器输出，专门钉死这两条容差。

### 🐛 Bug｜「日期太旧不采信」被说成了「没找到日期」

WM 这封信是 2025 年的，今天已经 2026 年，`due_date_not_stale`
（超过半年的过期日期一律不采信）把它标成不可信。
但界面把「不可信」一律翻译成「信里没有找到明确的截止日期」——
明明信上写着 7月2日，等于当着老人的面撒谎。

拆开：`fields.dueDate.stale` 独立于 `trusted`。

- 截止日期框：「信上写的截止日期是 2025年7月2日，这天已经过去了。」
- 顶部提示：「信上写的截止日期已经过去了，这封信可能是旧的」
  （原来说「没在信上找到截止日期」，和下面那句自相矛盾）
- 重拍提示：过期日期不再要求重拍 —— 重拍解决不了「这封信是去年的」

**最终效果**（浏览器实测，非 fixture）：
金额 87.05 ✅ 截止日 2025-07-02（标注已过期）✅ 发信日期不报 ✅ 重拍提示消失 ✅

### ✅ 变更｜告诉老人「过期了会怎么样」

只说「这天已经过去了」是把话说了一半。老人真正会问的是
「那会怎么样、要不要多交钱」。

而这句话信上本来就写着，只是我们以前没读：

```
If payment is received after 07/02/2025: $92.05
... a monthly late charge of 2.5% of the unpaid amount,
    with a minimum monthly charge of $5
```

新增 `fields.lateFee`，三个值全部照抄信上原文：

| 字段 | 来源 | WM 账单 |
|---|---|---|
| `amount` | 罚金锚点旁边的金额（必须带 $，遵守决定 06） | 92.05 |
| `ratePct` | `late charge of N%` | 2.5 |
| `minCharge` | `minimum monthly charge of $N` | 5 |
| `extra` | `amount - 应缴金额`（算出来的差额） | 5.00 |

界面上贴在截止日期框里、用一条分隔线隔开：

> ⚠️ 信上写着过了这天之后要交 92.05 美元，比原来多 5.00 美元，
> 之后每个月还会按没交的钱加收 2.5% 的滞纳金，最少 5.00 美元。

朗读也跟着念，紧挨在截止日期后面 —— 这两句要连在一起才有意义。

**三条自我约束**：
1. 信上没写就整段不出现。绝不说「一般会加收 10%」——
   各家公司罚则本来就不同（决定：期限规则不进知识库）。
2. 逾期价必须**大于**应缴金额，否则不采信 ——
   挡掉「把折扣价、分期价当成逾期价」的整类错。
3. 92.05 只能出现在这一段，绝不能跑进「要交多少」。
   slant 测试里有一条断言专门钉死这点。

比例和最低滞纳金要在**整页拼起来的文字**上找：这句话天生跨行
（`...minimum monthly charge` / `of $5, or such...`），逐行匹配永远差一截。
另外正则里不能用 `\b` —— PP-OCR 不输出词间空格，
整句粘成 `withaminimummonthlycharge`，`\bminimum` 永远匹配不上。

### ⚖️ 决定 07｜不再枚举整句，改枚举「零件」

**背景**：项目里手写了 84 条英文措辞（日期锚点 29、金额锚点 25、
句式词典 30）。每一条都是某封信教会我们的。
问题是英文写同一件事的方式无限，表是有限的：

```
if payment is received after 07/02/2025: $92.05     ← 表里有
payments received after the due date will incur...  ← 表里没有
a penalty of 10% will be added after...             ← 表里没有
```

继续加 `if`，第 200 封信还是会遇到没见过的写法。

**决定**：上面三句其实是同三个零件的不同排列。
枚举整句要 5×6×6 = 180 条；枚举零件只要 17 个词 + 一条组合规则。
把乘法搬到运行时做，而不是在表里预先展开。

新增 `frontend/src/utils/clues.js`：7 个词类 + 7 条组合规则。

| 词类 | 例词 |
|---|---|
| pay | payment / paid / remit / received / postmark |
| after | after / past due / beyond / later than / following |
| before | before / by / no later than / prior to / within |
| consequence | late charge / penalt / delinquen / assess / incur / failure to |
| deadline | due / deadline / expir / last day / must be received |
| total | total / balance / amount due / pay this |
| respond | respond / reply / return / submit / appeal / renew |

**三条自我约束**（写死在文件头，别再放宽）：

1. **永远是兜底**。明确锚点命中时它一句话都不说；
   组合分数一律 < 80，抢不走任何明确锚点。
   测试里有一条专门验证：同一封信里明确锚点和线索打架，必须信前者。
2. **只说「这句话在讲哪个字段」，绝不说「值是多少」**。
   值仍旧由空间匹配去找，所以抽出来的每个日期照样指得回
   OCR 的哪一行、哪个框 —— 决定 01 不受影响。
3. **每条线索带 why**，说明是哪几个零件凑出来的。
   出错时能一眼看出哪个词类太宽。

**词类正则一律不加 `\b`** —— PP-OCR 不输出词间空格。

**误报实测**：WM 账单 50 行里只有 3 行被线索点亮，其中一行
（`are canceled after initial acceptance you will be assessed...`）
语义上确实是误报 —— 但它旁边没有日期，空间层找不到值，等于零成本。
这正是「线索」和「值」分开的好处：**错的线索配不到值，就不会变成错的答案**。
