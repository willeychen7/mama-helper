一份文档讲完三件事。改代码之前看这里，改完之后记得回来改它。

- [**一 · 读信管线**](#一--读信管线) —— 一封信从被拍下到变成中文结论，经过哪七步

# 一 · 读信管线

```
拍照 → 图像预处理 → 本地 OCR → 空间字段抽取 → 交叉校验 → 中文模板 → 脱敏判定
       imagePrep    paddleocr-js   fieldExtractor   14 项      buildLayer0  contentRedactor
```

**整条链路零网络。** 飞行模式下功能照常 —— 这是可以当场验证的。

## 01 · 拍照 / 上传

**代码** `App.jsx › processImagePrivacy()`

HEIC 自动转 JPEG。原图只存在于当前请求的内存里，处理完立刻释放引用，不写入任何存储。

## 02 · 图像预处理

**代码** `utils/imagePrep.js`

不依赖 OpenCV，全部用 Canvas + TypedArray 手写，零新增下载体积。

| 步骤 | 做什么 | 闸门 |
|---|---|---|
| 纸张四角检测 | Otsu 分亮区 → 最大连通域 → `x±y` 极值定四角 | 面积、边长、对边比、内角、凸性，任一不过就跳过 |
| 透视矫正 | 手写 homography + 双线性重采样 | 已经是正的矩形就跳过，省一次重采样 |
| 去斜 | 投影剖面法，剪切近似代替真旋转 | 相对 0° 提升不足 2% 就当作本来是正的 |
| 去阴影 | 大半径盒式模糊估底色场，`gray / bg` | 底色已经均匀就跳过 |
| 对比增强 | 百分位拉伸 + 轻度非锐化掩模 | 同上 |

**输出两张几何一致的图**：`displayBlob`（彩色，给人看）和 `ocrBlob`（灰度增强，喂 OCR）。
几何一致意味着 OCR 返回的坐标以后可以直接画在预览图上。

> **踩过的坑 · 只降不升**
> 原来 `Math.min(1, max/long)`，727×294 的医院缴费联原样送进 OCR，
> 金额那几个字压根没进结果。现在长边低于 1600 会放大（最多 3 倍）。
>
> **踩过的坑 · 有损压缩**
> OCR 用图曾用 JPEG 0.95，细笔画被色度二次采样打伤（实测命中 3/4 → 2/4）。
> 这张图不出浏览器，体积毫无代价 —— 现在用 PNG 无损。

## 03 · 本地 OCR

**代码** `@paddleocr/paddleocr-js`，PP-OCRv6 优先、v5 回落，WebGPU 优先、WASM 兜底

实测置信度：数字类 token **97.8%**、日期 **99.3%**、长句子 95.9%。

**OCR 不是准确率瓶颈。** 我们遇到的字符错误几乎全在长句子里（`Lean Power`、
`Ses mel`），而长句子不参与字段抽取。

> **踩过的坑 · 空格**
> PP-OCR 输出英文**不带词间空格**（`AMOUNTYOUOWE`、`Sub-TotalofCPAGenerationCharges`），
> 而所有锚点正则写的是 `\s+` —— 四张真实账单的金额因此全部抓不到。
> 改成 `\s*` 之后从 0 到全对。
>
> 注意：`\s*` 不能无脑全局替换。挨着无界重复组（`(\s+X)*`）会导致灾难性回溯，
> 那些必须保留 `\s+`。判据是**量词有没有界**。
>
> **还在的坑 · 小数点**
> 可能整个丢失（`$59.94` → `$5994`），且置信度 100%。靠置信度筛不掉，
> 只能靠上下文（见 05）。

## 04 · 空间字段抽取

**代码** `utils/fieldExtractor.js`

**不把 OCR 拍平成一段文字。** 账单的语义有一半住在空间关系里 ——
标签在左、数值在右，金额靠右对齐成一列。拍平的那一刻这些信息就没了。

**匹配策略**（按优先级）

1. 锚点右侧、同一行、最近的
2. 锚点正下方、水平重叠、3 行高之内
3. 锚点自己这一行里就带着值

**辅助结构**

- **右对齐金额列聚类** —— 按 `right` 坐标分簇，最大簇即金额列
- **分项求和关系** —— 在列里搜索「连续若干项之和 = 某一项」，找到就是强证据

**词典规模** 见 [下方自动生成块](#词典规模)，不手写。

> **这一层是错误的主力。** v1 的 27 个 bug 里 14 个出在这里，而且性质最危险 ——
> 产出的是**自信的错误答案**，不是「看不清」。
>
> 四类根因：同一意思英文有无数写法 / 同一词组在不同上下文意思相反 /
> 格式歧义（CR、括号负数、逗号小数点）/ 版面歧义（一张账单八个金额）。

## 05 · 交叉校验

**代码** `fieldExtractor.js › addCheck()`，14 项

抽出来的字段必须通过校验才被标记为可信。
**这是整套系统里唯一能「知道自己什么时候不该被相信」的部分。**

| 校验 | 防什么 |
|---|---|
| 分项之和 = 小计 | OCR 把某一位数字读错 |
| 金额需有佐证 | 孤零零一个数字就当成应缴款 |
| 明确写着不用交 | `AMOUNT DUE: None` 被无视 |
| 小数点合理性 | 没有小数点、且比同页其他金额大 15 倍以上 |
| 日期不陈旧 | 半年前的日期被当成待办 |
| 发信日期不在未来 | 年份认岔，信「写于」明年 |
| 发信日期早于截止日 | 两个日期读反了 |
| 类别内容分 | 只凭机构名就断定信件类型 |
| 无冲突总额 | 两个强锚点给出不同金额 |
| OCR 置信度 | 值所在行置信度低于 60% |

**佐证条件**（满足任一即可）：分项求和通过 / 在金额列里 / 标签与数字同行且锚点够强 /
同一数字页面上出现两次以上。

## 06 · 中文模板生成

**代码** `fieldExtractor.js › buildLayer0()`

回答老人真正关心的五件事：**这是什么信 · 谁寄的 · 大意 · 金额 · 什么时候之前**。

全部由模板拼成 —— 不联网、不调模型、**不会幻觉**、今天和明天说的一模一样。

**金额有三种状态，必须分清**

| 状态 | 说法 | 搞混的后果 |
|---|---|---|
| 要交 | 「要交 99.36 美元」 | — |
| 自动扣款 | 「会自动从您的账户扣走，不用另外去交」 | 说成「要交」→ 老人交第二遍 |
| 不用交 | 「这次不需要付款」/ 贷记余额说明 | 说成「要交」→ 白交一笔 |

**日期有两种，永远分开显示**

| | 是什么 | 卡片上 |
|---|---|---|
| **截止日期** due date | 你必须在这天之前做点什么 | 红框，加一句「要在这天之前办」 |
| **发信日期** statement date | 这封信是什么时候写的 | 灰框、细边、小字，加一句「不用在这天之前办什么」 |

**这两个混在一起是最容易害老人做错事的一类错。** Hoag 那张医院账单上只有
`STATEMENT DATE 10/19/18`，根本没有到期日 —— 把它显示成「请在 2018年10月19日
之前处理」就是凭空造出一个期限。

光靠「发信日期」四个字不够，那是行话。所以除了分框、降低视觉重量，还直接写明
**「不用在这天之前办什么」**。

没有标签的信头日期（政府信、法院信常见，`April 24, 2024` 孤零零一行）也抽，
但卡死四个条件：整行只有日期 · 在页面上三分之一 · 不在未来 · 没有任何带标签的发信日期。
**带标签的永远优先** —— 标签是信上白纸黑字写的，位置是猜的。

**紧急度** 红橙黄绿四档，最紧急再叠 `‼️`。提示语按**真实原因**生成，不按等级套现成的话。

> **踩过的坑 · 模板句陈述未验证的事实**
> 写死的「小助手只确认了金额和日期」，而下一行写着「没有找到截止日期」。
> 现在 `fieldExtractor.consistency.test.mjs` 会自动断言这类自相矛盾。
>
> **踩过的坑 · 把「没读懂」说成「不紧急」**
> 词典一条没命中时，原来输出「没有发现特别紧急的措辞」。
> 一封写着「30 天内不回应视为放弃权利」的法院信会被这样描述。
> **沉默必须沉默得诚实：不懂就说不懂。**

## 06.5 · 重拍提示

**代码** `fieldExtractor.js › retakeHints`

抽不出金额或日期时，不只说「没能确认」，还要说**该怎么办**。

系统本来就知道自己为什么失败——「有一个字号 1.5 倍、在页面顶端的金额，
但它没有被任何锚点认领」。把这个原因翻译成老人能照做的一句话：

> 📷 信上的金额和日期都很显眼，但它们旁边那行标签没能读出来。
> 请把整张单子重新拍一次，特别是最上面那一行字。

**只为「金额」和「截止日期」开口。** 姓名、地址、账号缺了一个字都不说 ——
老人很可能是故意不拍的。见 [`journal.md`](journal.md) 决定 05「默认不问」。

> **为什么这条比加词典值钱**
> 它不解决任何一封具体的信，它解决「照片里缺了信息」这一整类。
> 实测：把被裁掉的标签补回原位，WM 那封账单的金额立刻从「没能确认」
> 变成「要交 87.05」—— 老人重拍一次就够了。
>
> **这里原来是一遍「关键区域二次 OCR」（裁剪+放大+重认+替换），已删除。**
> 它从没改善过任何一行，有确认的污染机制，而且实测救不回被切掉的字。

## 06.6 · 版面还原（给 LLM 用的文本）

**代码** `utils/layoutText.js`

**一封账单是二维的。把它按行拼成一段文字，二维信息在那一刻就没了。**

真实例子（WM 垃圾账单，拼平之后）：

```
online tools for billing and more. Have a
07/02/2025: $ 92.05                          ← 右栏的金额插进了左栏句子中间
question? Check our support center or start

Previous Balance / Payments / Adjustments / Current Invoice / Total Account
+ / + / + / Charges / Balance Due
0.00 / 0.00 / 0.00 / 87.05 / 87.05           ← 哪个数字属于哪一栏，全丢了
```

按坐标摆回二维之后：

```
    Previous Balance   Payments    Adjustments   Current Invoice   Total Account
                                                    Charges         Balance Due
                          +            +                              87.05
        0.00            0.00         0.00           87.05
```

代价是 **+45% 字符**（多出来的基本是空格）。

> **这个函数不排序、不猜阅读顺序。** 只按坐标摆回去。
> 「谁该读在谁前面」留给看到版面的那一方判断 —— 我们自己猜反而会猜错。
>
> **注意**：传进去的必须是**已经脱敏过**的行。这个函数只管排版，不认识 PII。

**为什么现在才做**：字段抽取用的是 bbox 几何，根本不看阅读顺序，所以一直没暴露。
**一旦要把文字发给 LLM，顺序就突然变成头等大事了。**

## 06.8 · 知识库（理解层）

**代码** `knowledge/knowledge.js` + `knowledge/knowledge.json`

模板词典只有 30 条，覆盖不了长尾。知识库补的就是这一块 ——
但它补的是**「这类信是什么」，不是「这封信的答案」**。

```
本地 OCR → 本地脱敏 → 多标签匹配 → 查知识库 ──┐
                                              ├─→ 组合
        本地抽取 + 交叉校验过的金额/日期/机构 ──┘
```

**知识库里存什么**

| 字段 | 内容 |
|---|---|
| `whatItIs` | 这类信是什么 |
| `purpose` | 常见目的 |
| `typicalAction` | 通常需要什么行动 |
| `deadlineRule` | **期限规则**，分两档 —— 见下 |
| `risks` | 不处理会怎样 |
| `sources` | 官方来源链接 |
| `signals` | 识别信号（强/弱两档） |

**绝不存什么：金额、年份、某一封信的事实。**

一旦事实进了知识库，它就从「知识」变成了「可能过期的谎话」，而且没有任何办法验算。
`knowledge.test.mjs` 会逐条机械检查这一点 —— 光靠 code review 守不住，
词条会越来越多，谁都可能顺手写一个数字进去。

**`deadlineRule` 是可选字段**

只有**写在法律法规里、全州或全国统一**的期限才填，而且必须写明依据。
现在 38 条里只有 6 条有。

「这家公司通常给 30 天」这种**不填** —— 电费按出账日算、医院按科室算、
HOA 按规约算，每家都不同，写一个数字出去就是编。不填的时候界面自然只说
「没在这封信上读到期限」，不多嘴。

> 我第一版给 32 条各写了一句一模一样的「以信上印的为准」，还配了断言去检查。
> **同一句话存 32 遍不是设计，是官僚主义** —— 那句话本来就该由界面
> 在读不到期限时自己说，不该存进数据里。已删。

> **月日可以，年份不行。**> **月日可以，年份不行。**
> 「房产税 11 月 1 日到期、12 月 10 日之后加罚」是年年重复的法定规律，属于知识；
> 「2026 年 11 月 1 日」是某一封信上的事实，必须来自 OCR。

**多标签，不是单选**

一封信可以同时是「HOA 违规通知」和「催缴」。硬选一个会丢掉真正要紧的那一面。
所以 `matchDocumentTypes` 返回**排序后的全部命中**，由 `resolveDocumentTypes` 决定说几个：

| 结局 | 什么时候 | 怎么说 |
|---|---|---|
| `confident` | 头名分数够高且甩开第二名 | 说一个 |
| `ambiguous` | 前两名咬得很紧 | **两个都说**，不假装只有一个 |
| `unknown` | 分数都不够 | 明说不认识，**不猜** |

**每一句话都标明出处**

组合出来的每一行都带 `source` 标签：

- `letter` —— 事实是从**这封信上**读出来并通过交叉校验的
- `knowledge` —— 讲的是**这类信**的常识，跟手上这封的具体内容无关

为什么非要分：知识库里写着「白卡复审通常给 30 到 60 天」。不加区分地说出来，
老人会以为「我这封信给了 30 天」—— 那就是凭空造了一个期限，
跟早期从电话号码里凑出假截止日一样糟。

**所以读到确切期限时，就不再讲规律** —— 两个一起说会让人分不清哪个才是自己的。

# 二 · 隐私处理

## 核心原则

**让隐私成为可以被证伪的事实，而不是一句需要相信的承诺。**

```
第一档  "我们加密传输"        用户无法验证，只能选择信或不信
第二档  "我们不存储"          用户仍然无法验证
第三档  "数据根本没离开设备"   可以被证伪，因此可以被相信   ← 我们在这里
```

第三档的力量不在于更安全，**在于可验证**。老人自己不会验证，
但做决定的是子女 —— 一个能自己动手确认的东西，比一句要靠相信的话有说服力得多。

## 当前状态：零网络

从拍照到老人看见中文结论，**整条链路一次网络请求都没有**。

**验证方法：把手机调成飞行模式，拍一张信。功能照常。**

这是任何隐私政策都替代不了的验证方式，也是这个项目相对同类产品的结构性差异 ——
它们的架构是默认上传、本地处理是新机型的加分项，方向相反。

## 什么留在设备上

| 内容 | 状态 |
|---|---|
| 信件照片原图 | **不出设备**（内存中处理，完成后释放引用） |
| OCR 文字结果（含姓名、地址、账号） | **不出设备** |
| 金额 · 日期 · 机构 · 类别 | **不出设备**（本地抽取 + 本地校验） |
| 中文解释文案 | **不出设备**（本地模板拼句，无模型参与） |
| 脱敏后的信件正文 | **需显式开启**（为将来接 LLM 准备，目前只计算不发送） |

## 逐行六道关卡

**方向是白名单**：只有六道关全过的行才允许外发。

这样拦不准的代价落在「少发几句、翻译不完整」，而不是「账号被发出去了」。
**这个方向是刻意选的** —— 因为老人看不懂英文，没法替我们把关，
所以不能采用「先发出去、漏了再说」的思路，必须让**漏检不会造成泄露**。

| 关卡 | 拦什么 | 实现要点 |
|---|---|---|
| 1 · 正则 PII | SSN、信用卡、路由号、驾照、Medicare 号等 16 类 | 有校验位的靠校验位（Luhn 等），误报率低 |
| 2 · 姓名特征 | 「姓, 名」格式、称呼、带标签字段、位置形状 | 配**文档常用词表**排除栏目名误判 |
| 3 · 收件人区块 | 整块盖掉，不逐词判断 | 按内容边界扩展，遇机构名或金额即止 |
| 4 · 地址 | 街道、城市州邮编、信箱 | 机构地址放行、收件人地址必挡（见下） |
| 5 · 编号型字符串 | 按**形状**拦，不枚举 | 仅带机构投递标签的例外放行 |
| 6 · 网址 / 邮箱 | 域名与抬头机构名对不上就拦 | 个人邮箱域名一律拦 |

**在被拿掉的位置留占位符** `[个人信息已在本机隐藏]`。
不留的话模型会把前后两句错误缝在一起，编出信里根本没有的意思。

## 寄件方 vs 收件人

地址长得一模一样，性质完全相反：

- **收件人地址 = 老人的家** → 必须挡
- **寄件方地址 = 支票往哪寄、电话打哪里** → 挡了反而有害

全挡掉看似安全，实则让翻译少了最实用的一半。

**判据**：这段内容挨着的是**机构名**还是**人名**。两边都挨不上就按挡掉处理。

实例（Hoag 医院账单，见 `contentRedactor.hoag.test.mjs` 的 13 条断言）：

```
✅ 放行   Hoag Orthopedic Institute          机构抬头
```

> **踩过的坑 · 机构词表太窄**
> `ORG_HINTS` 漏了 `institute`，于是整个
> `HOAG ORTHOPEDIC INSTITUTE / MAILSTOP / PO BOX / DALLAS, TX` 被当成收件人地址挡掉。
>
> **踩过的坑 · 拿宽词表当机构锚点**
> `ORG_HINTS` 含 `service`，于是 SCE 账单上的「Service account」被当成机构名，
> 紧跟其后的**账号和服务地址被判定为机构信息放行了** —— 这是最严重的一次泄露。
> 现在分成两张表：宽表判断「不是人名」，**严格表**才能当机构锚点。

## 发送前可见

界面上有一块「信件大意翻译」，展开就是**一旦接上后端会发出去的全部原文**，
以及被挡下的每一条及其原因。

**这是接 LLM 之前唯一一次能检查的机会**，所以它在功能上线之前就已经存在了。
但它的定位是**知情**，不是**安全机制** —— 用户看不懂英文，指望他把关等于没有把关。

## 威胁模型

诚实声明比夸大声明更值得信任，尤其面对真正做决定的子女。

**防**

- 服务商（我们自己）看到用户的信
- 网络传输被窃听
- 我们被黑了影响到用户 —— 因为我们手上没有他们的数据

**不防**

- 有人拿到解锁的手机
- 浏览器或操作系统层面的攻击
- 用户自己截图转发
- **通过类别推断** —— 知道他收到白卡复审通知，约等于知道他是低收入。
  即使只发枚举值，量很小但不是零。

## 最薄弱的一环

**PII 检测仍然是正则，人名靠形状猜。**

`BAKER, NATE` 能抓到是因为「姓, 名」这个形状，换成 `Nate Baker` 就会漏。

而这是唯一一个**漏了没有任何人会发现**的模块 —— 金额错了有分项求和能拦，
人名漏了没有任何校验和能验证它。

**下一步**：接本地 NER 模型（14.7 MB ONNX，浏览器内 WASM 约 13ms、WebGPU 约 4ms，
首次下载后缓存离线可用），**与现有规则并联，任一命中即挡**。
模型补人名地址，规则补编号和机构语境判断。

依据见 [`journal.md`](journal.md) 的「决定 02」。

# 三 · 准确率验证

## 核心原则

**金额和日期错 = 不通过，没有例外。**
对老人报错一个金额，比说「我看不准」糟糕得多。

**「没找到」不等于「错」。**
六封测试信里有五封本来就没有截止日期。分不清这两者，
就会去追一个不存在的 bug —— 这个错我们犯过。

**说「看不准」永远比猜对更安全。**
校验不过就退回兜底文案，不硬猜。

## 加一封新信的完整步骤

**这是目前投入产出比最高的事。**
每加一张真实信件，都可能像那封 AT&T 账单一样冒出全新的失败模式 ——
它一封就贡献了 5 个 bug。

### 1 · 放图

照片放进 `demo_image/`。敏感的先涂掉姓名地址，但**保留金额、日期和栏目标签** ——
那才是被测的东西。

> 🔒 **真实信件不要提交到 git。**
> 已入库的 `demo_ocr_pp.json` 里那六封是公开样本账单（姓名金额都是编的），可以提交。
> 但只要放进一封真实的信，它的 OCR 文本就含有真实 PII。
> 真实样本放 `demo_image/real/`（已在 `.gitignore` 里），OCR 结果存成 `private_*.json`。

### 2 · 跑 OCR

```bash
cd frontend/src/utils
pip install rapidocr-onnxruntime      # 模型打包在 wheel 里，不需联网
python3 pipeline_ppocr_lines.py
```

用的是 PP-OCR 模型族，产出的行结构和浏览器里的 PaddleOCR 一致
（同一张 SCE 账单，两边都是 53 行）。

### 3 · 人工看**原图**标真值

打开原图，把四个字段填进 `ground_truth.json`：

```json
"新账单名": {
  "note": "描述这封信的特殊之处，以及为什么真值是这样",
  "category": "electric",
  "sender": "SCE",
  "amount_shown": 99.36,
  "payment_action": "pay",
  "due_date": null,
  "today": "2024-02-10"
}
```

> ⚠️ **必须看图，不能看 OCR 结果。** 否则就是拿答案对答案。

**`payment_action` 三选一**：`pay`（要交）/ `autopay`（自动扣款）/ `none`（不用交）

**`amount_shown` 和 `payment_action` 是两件事** —— 一张写着
`Total Premium $165.00` 但 `AMOUNT DUE: None` 的保单，
金额是 165，付款方式是 `none`。混在一起会漏掉整整一类错误。

### 4 · 标注拍摄时点

`today` 填这封信当年的日期。否则两年前的账单会被「陈年旧件」规则**正确地**拒绝，
测出来的是测试环境伪影，不是真实表现。这个坑我们踩过。


红了就看 `checks` 数组，能直接定位是哪一环断的。

## 关于样本量

当前 6 封真实信件，其中 3 封是网上的样本账单而非老人真实收到的信。

**这个样本量下的满分只能说明「没有明显硬伤」。**

所以扩样本的优先级高于写新代码。

特别想要的三类（最可能炸出新问题）：

- **手机实拍的**（不是数字扫描件）
- **医疗 EOB**（格式最复杂）
- **政府信件**（社安局、白卡 —— 后果最严重的一类）
